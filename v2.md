# AI Agent — v2 Architecture & Feature Plan

This document captures the planned evolution of the AI server administration agent: remote LLM inference, multi-host command execution, streaming responses, and related design decisions. It is intended as a readable reference for implementation later.

**Already in the tree (do not re-implement):** `LLMProvider` + `create_llm_provider`, one `OllamaProvider` over `LlmHttpSession`, configurable `OLLAMA_HOST` for local or remote Ollama, vendor-neutral `LLMErrorKind`, startup-fatal vs mid-turn-recoverable CLI errors, streamed assistant text, and `ai-agent-llm` (warmup + local Ollama-compatible facade that prints a bind URL). Still open: SSH-tunneled inference, and `ExecutionBackend` for remote commands.

## Design principles (carry forward from v1)

These remain non-negotiable in v2:

| Principle | Meaning |
|-----------|---------|
| **LLM is untrusted** | Tool arguments are attacker-controlled; policy validates everything |
| **Agent is local trust boundary** | Policy, approval, audit, and CLI stay on the client machine |
| **No raw shell** | Commands use argv + structured `CommandExpr`; never `/bin/sh -c` with model strings |
| **Human approves consequential actions** | Risk tiers + confirmation; model cannot self-approve |
| **Explicit completion** | Model uses `respond(message, finished)` — not plain assistant text |
| **Linux permissions are the OS boundary** | Dedicated `ai` user, no sudo by default |

v2 adds **where** inference runs and **where** commands run as configurable dimensions — without collapsing those responsibilities.

## Three roles: client, inference, execution

The key insight for v2 is to **stop conflating** three separate machines:

```text
┌─────────────┐     ┌──────────────┐     ┌─────────────────┐
│  Your PC    │     │  LLM host    │     │  Target host(s) │
│  (Client)   │     │  (Inference) │     │  (Commands)     │
├─────────────┤     ├──────────────┤     ├─────────────────┤
│ Agent CLI   │────▶│ Ollama/GPU   │     │ Ubuntu server   │
│ Approvals   │     │ qwen3.5 etc. │     │ another box     │
│ Audit log   │     │              │     │ localhost       │
└─────────────┘     └──────────────┘     └─────────────────┘
```

| Component | Production preference | Responsibility |
|-----------|----------------------|----------------|
| **Agent** | Runs **locally** (laptop/desktop) | Loop, policy, approval UX, audit logging |
| **LLM** | Runs **remotely** (GPU machine) | Reasoning, tool selection, final answers |
| **Command execution** | Runs on **any configured host** | Actually executes approved argv commands |

All three roles are **independent**:

- LLM on GPU box
- Commands on headless Ubuntu admin server
- Agent + human on laptop

For testing and flexibility, **everything can still run locally** — same code paths, different configuration (strategy pattern + config, not a forked codebase).

## Streaming final responses

### What it means today (v1 — batch)

```text
You press Enter
  → agent loop runs (possibly many tool calls)
  → Ollama generates the full answer in one HTTP request
  → when the HTTP call finishes, the entire reply appears at once
```

The user waits on a blank screen, then gets a wall of text.

### What streaming would do (v2)

Ollama sends the answer **token-by-token** (or chunk-by-chunk) over HTTP. The CLI **prints as it arrives**:

```text
AI: Technical Debt Radar is a Scala project that…
    ↑ words appear incrementally while the model is still generating
```

### What streams vs what does not

| Streams in v2 | Does **not** stream (unchanged) |
|---------------|----------------------------------|
| Final `respond(message=…, finished=true)` text | Tool calls, policy checks, approvals |
| User-visible answer | Command stdout/stderr returned to the model |
| | Audit events, batch preview prompts |

**“Streaming final responses”** is **not** streaming `docker ps` output to the terminal. It is making the **last user-facing message** feel responsive instead of blocking for 5–30 seconds and dumping everything at once.

### Implementation notes

- Use Ollama `/api/chat` with `"stream": true`
- CLI: Rich `Live` or incremental markdown rendering
- Stream only when the model calls `respond(finished=true)` (or equivalent final path)
- Tool-calling iterations remain non-streaming batch requests

## Layer 1: LLMProvider — local vs remote inference

v1 already has an abstract `LLMProvider` with `OllamaProvider`. v2 extends this with configuration — not a rewrite.

```text
LLMProvider (abstract)
├── OllamaLocalProvider     → http://localhost:11434
└── OllamaRemoteProvider    → http://gpu-box:11434
                              OR SSH tunnel
                              OR custom API gateway
```

### Remote access options for the model

| Approach | Pros | Cons |
|----------|------|------|
| **Direct HTTP** to remote Ollama (`OLLAMA_HOST=http://192.168.x.x:11434`) | Simplest | Ollama must be reachable; requires firewall discipline |
| **SSH port forward** (`ssh -L 11434:localhost:11434 gpu-box`) | No exposed Ollama on LAN | Manual or managed tunnel lifecycle |
| **Remote API wrapper** (small proxy service on GPU box) | Auth, TLS, rate limits | Extra service to build and maintain |

**Recommendation for v2 v1 of remote inference:** direct HTTP to Ollama on the GPU machine (firewall-restricted), or SSH tunnel for dev. The existing `OllamaProvider` may only need a different `OLLAMA_HOST` — not necessarily separate classes on day one.

### Example configuration

```env
LLM_PROVIDER=ollama
OLLAMA_HOST=http://192.168.1.50:11434
OLLAMA_MODEL=qwen3.5:latest
```

Optional later: `OllamaSshTunnelProvider` that starts/stops an SSH tunnel before chat calls.

## Layer 2: ExecutionBackend — commands on any machine

Separate from LLM placement: **where approved commands actually run**.

```text
ExecutionBackend (abstract)
├── LocalBackend           → subprocess argv on the agent host (your PC)
├── SshBackend             → structured argv over SSH (no remote shell string)
└── (future) AgentDaemonBackend → small trusted daemon on target speaking argv protocol
```

**Policy engine and approval UX always stay on the local agent.** Only the **executor** changes based on the selected target.

The model must **not** embed `ssh user@host` inside argv. The agent resolves the target and constructs SSH invocation after policy + approval.

## Schema extension: the `target` parameter

Keep argv pure. Add **execution context** as a separate tool parameter.

### Example: run on local machine

```json
{
  "target": "local",
  "command": {
    "type": "single",
    "argv": ["docker", "ps"]
  },
  "reason": "Check containers on this machine"
}
```

### Example: run on named remote server

```json
{
  "target": "home-server",
  "command": {
    "type": "single",
    "argv": ["systemctl", "status", "nginx"]
  },
  "reason": "Check nginx on the home server"
}
```

### Approval display (shown to user)

```text
Target: home-server (ssh://ai@192.168.1.10)
Command: systemctl status nginx
Risk: READ_ONLY
```

The `target` field is **not** part of the raw argv passed to the binary. It is metadata consumed by the agent’s execution router.

### Apply to all command tools

- `run_command` — add required `target`
- `run_commands` — add required `target` (same target for the whole batch, or per-command target in a later revision)

System prompt and tool schema must list **allowed target names** — the model picks from an allow-list, not arbitrary host strings.

## Named execution targets (config)

Targets are defined in configuration — **not** free-form IPs/hostnames from the model.

```yaml
# execution_targets.yaml (or merged into agent config)

execution_targets:
  local:
    backend: local
    description: "This machine (where the agent CLI runs)"

  home-server:
    backend: ssh
    host: 192.168.1.10
    user: ai
    identity_file: ~/.ssh/id_ed25519
    description: "Ubuntu admin server"

  gpu-box:
    backend: ssh
    host: 192.168.1.50
    user: ai
    identity_file: ~/.ssh/id_ed25519
    description: "GPU machine (Ollama host)"
```

Environment override example:

```env
AGENT_DEFAULT_TARGET=local
AGENT_EXECUTION_TARGETS_FILE=./execution_targets.yaml
```

Policy may restrict which targets accept which risk tiers (e.g. DESTRUCTIVE only on `home-server`, never on `local`).

## Three execution scenarios

| Scenario | `target` | Backend | Typical use |
|----------|----------|---------|-------------|
| Debug Docker on Windows dev PC | `local` | `LocalBackend` | Development and testing |
| Admin Ubuntu server (production) | `home-server` | `SshBackend` | systemctl, journalctl, docker |
| Inspect GPU machine itself | `gpu-box` | `SshBackend` | `nvidia-smi`, disk space on LLM host |

**LLM host and command host do not have to be the same.**

Common production layout:

```text
  Laptop                    GPU box                  Admin server
  ┌──────────┐             ┌──────────┐             ┌──────────┐
  │ Agent    │──HTTP──────▶│ Ollama   │             │ docker   │
  │ You      │             │          │             │ nginx    │
  │ Audit    │──SSH───────────────────────────────▶│ journal  │
  └──────────┘             └──────────┘             └──────────┘
       │                          │
       │                          └── optional: commands here too
       └── commands local (Windows dev only)
```

## SSH execution security

Remote execution must mirror local argv rules:

| Rule | Implementation |
|------|----------------|
| **No remote shell strings** | Never `ssh host 'bash -c "…"'` with model output |
| **Structured remote argv** | `ssh user@host docker ps -a` as discrete argv over SSH |
| **Same policy engine** | Binary/subcommand allow-list; risk tiers per segment |
| **Same approval UX** | Show target + rendered command + risk |
| **Audit everything** | Log `target`, `rendered_command`, `resolved_host`, result |

Additional SSH-specific concerns:

- Dedicated `ai` user on each target; no sudo by default
- `known_hosts` / strict host key verification
- Targets only from config — **never** model-supplied IP addresses or hostnames
- Optional: per-target policy overlays (Linux server policy vs Windows local policy)
- Document that SSH keys on the agent host are high-value credentials

## How the pieces fit together

```text
                         ┌──────────────────────┐
                         │      AgentLoop       │
                         │   (always local)     │
                         └──────────┬───────────┘
                                    │
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
       ┌─────────────┐      ┌─────────────┐      ┌─────────────────┐
       │ LLMProvider │      │PolicyEngine │      │ ExecutionRouter │
       │ local/remote│      │ (+ target)  │      │ local / ssh / … │
       └──────┬──────┘      └─────────────┘      └────────┬────────┘
              │                                            │
              ▼                                            ▼
       GPU machine                                   Target machines
       (Ollama)                                      (local, servers, …)
```

### Request flow (single command)

```text
User message
    │
    ▼
AgentLoop ──▶ LLMProvider.chat(messages, tools)
    │
    ▼
Model returns run_command(target, command, reason)
    │
    ▼
PolicyEngine.evaluate(command) + validate target exists
    │
    ▼
ApprovalPrompter (show target + command + risk)
    │
    ▼
ExecutionRouter.resolve(target) ──▶ ExecutionBackend.run(command)
    │
    ▼
Structured result ──▶ LLMProvider ──▶ … until respond(finished=true)
    │
    ▼
Final message to user (optionally streamed)
```

### Class responsibilities

| Class / module | Responsibility |
|----------------|----------------|
| `LLMProvider` | Chat, tools, warmup, optional streaming — **where inference runs** |
| `PolicyEngine` | Validate `CommandExpr`, risk tier, forbidden patterns |
| `ApprovalPrompter` | Human confirmation, batch preview, session grants |
| `ExecutionRouter` | Map `target` name → `ExecutionBackend` instance |
| `ExecutionBackend` | Run approved argv on a specific machine |
| `AuditLogger` | Record target, command, approval, outcome |

## Suggested implementation order

### Phase A — Remote LLM, local execution (smallest step)

**Status: done** except a managed SSH tunnel (still planned).

1. `OLLAMA_HOST` may point at a remote GPU box; local Ollama still works
2. Warmup, tools, and `respond` use the same HTTP session over that host
3. README covers LAN HTTP, firewall caution, and connection-error behavior

**Outcome:** Agent on laptop, model on GPU, commands still local (current behavior + config).

### Phase B — Multi-host execution

4. Define `execution_targets.yaml` schema
5. Implement `ExecutionBackend` interface + `LocalBackend` (refactor current executor)
6. Implement `SshBackend` for one remote target
7. Add `target` to `run_command` / `run_commands` tool schema
8. Show target in approval UI and audit log
9. System prompt lists allowed targets per session

**Outcome:** Commands on home server; LLM still remote; agent local.

### Phase C — UX polish

10. Streaming final `respond` messages
11. Session persistence (save/resume conversation)
12. Policy packs per target (`windows-dev.yaml`, `linux-server.yaml`)

### Phase D — Vision & attachments

13. `attach_image(path)` with SENSITIVE_READ + user approval (path user provides)
14. `capture_screenshot(...)` with platform utility + strict confirm
15. Requires vision-capable model (`qwen3.5:latest`, etc.)

### Phase E — Production hardening

16. Web UI or thin remote API (same approval token model)
17. Optional `AgentDaemonBackend` if SSH proves insufficient at scale
18. Notifications when approval is required

## SSH design choice

**Where does SSH originate?**

| Option | Description |
|--------|-------------|
| **Recommended** | SSH always from the **agent host** (your laptop) to admin targets |
| Alternative | Jump host or daemon on LLM box — only if network topology requires it |

For the described setup (agent local, LLM remote, commands on admin server):

```text
  [Your PC / Agent]  ──SSH──▶  [home-server: ai@192.168.1.10]
  [Your PC / Agent]  ──HTTP──▶  [gpu-box: Ollama :11434]
```

You need SSH keys from the **agent machine** to each execution target. The LLM machine does not need to SSH on your behalf unless you explicitly design it that way.

## Future features (brief)

Features discussed for v2+ that complement this architecture:

### Streaming (detailed above)

Final response streaming only — not tool output streaming.

### Screenshots / vision

| Variant | Description | Risk |
|---------|-------------|------|
| `attach_image(path)` | User saves screenshot; agent reads approved path | SENSITIVE_READ — always confirm |
| `capture_screenshot(...)` | Agent triggers capture after approval | SENSITIVE_READ — always confirm |

- Use scratch dir for temp files; audit the event, not image bytes
- Vision requires multimodal `LLMMessage` (images as base64) + vision-capable Ollama model
- On headless Linux servers, disable capture; allow attach from inbox directory only

### Other candidates

| Feature | Notes |
|---------|-------|
| Session persistence | Resume conversations; tie to audit session id |
| Policy packs | Domain bundles: docker, nginx, homeassistant |
| Dry-run mode | Policy + render command without execute |
| Text file attach | Lower risk than screenshots; proves file → model path |
| Git read-only tools | `git log`, `git diff` in policy — useful for code understanding |
| Web UI | Same `respond` + approval model as CLI |

## Summary

v2 separates three concerns that v1 implicitly combined:

1. **Where the agent runs** — always local (trust + UX)
2. **Where the LLM runs** — configurable via `LLMProvider` / `OLLAMA_HOST`
3. **Where commands run** — configurable via `ExecutionBackend` + `target` in tool schema

The model proposes `{ target, command, reason }`. The agent validates, shows the user **target + command + risk**, executes through the appropriate backend, and returns structured results until `respond(finished=true)`.

Local-all-in-one remains a configuration profile, not a separate product. Production adds remote Ollama and SSH execution targets — same strategy pattern, same security model, same approval UX.
